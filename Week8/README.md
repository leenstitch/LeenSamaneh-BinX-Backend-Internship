## EF Core Query Logging

EF Core SQL logging was enabled during development:

```csharp
.LogTo(
    Console.WriteLine,
    LogLevel.Information)
```

Sensitive data logging was also enabled for development/debugging:

```csharp
.EnableSensitiveDataLogging()
```

This allowed us to inspect the SQL generated by EF Core and count the actual database queries executed by the endpoints.

## N+1 Investigation

N+1 occurs when an application executes one query to retrieve a list and then executes an additional query for each item to retrieve related data.

For example:

```text
1 query for the list
+
1 query for each item
=
N+1 queries
```

The `My Bookings` repository query was:

```csharp
public async Task<IEnumerable<Booking>> GetMyBookingsAsync(int photographerId)
{
    return await _context.Bookings
        .Include(b => b.Customer)
        .Include(b => b.SessionType)
        .Where(b => b.PhotographerId == photographerId)
        .OrderBy(b => b.StartTime)
        .ToListAsync();
}
```

The query was inspected using EF Core SQL logging.

The generated SQL used `JOINs` to retrieve the related `Customer` and `SessionType` data instead of executing one additional query for every booking.

Therefore, no genuine N+1 problem was found in this endpoint.

### Tested Endpoints

| Endpoint      | Database Queries | N+1 |
| ------------- | ---------------: | --- |
| My Bookings   |                2 | No  |
| Session Types |                1 | No  |
| Notifications |                1 | No  |

The `My Bookings` request executed two queries in total:

1. Retrieve the photographer profile.
2. Retrieve bookings with their related data.

## Test Data

The LensBook database already contained more than 50 realistic records in the main tables, so additional seeding was not required.

## Result

The tested endpoints did not show a genuine N+1 query problem. The SQL logging provided a measured baseline for the optimization work in the following days.

# Day 2 — EF Core Query Optimization

## Goal

Optimize EF Core queries by reducing unnecessary data retrieval and understanding different loading strategies.

## Eager Loading with Include

The original `GetMyBookings` query used:

```csharp
.Include(b => b.Customer)
.Include(b => b.SessionType)
```

This is an example of **Eager Loading**, where related entities are loaded together with the main entity.

The SQL generated by EF Core used `JOINs` to retrieve the related data.

Although this did not produce an N+1 problem, the endpoint did not require all of the related entity data in its response.

## Projection

The query was optimized using LINQ projection with `Select()` and `BookingResponseDto`:

```csharp
.Select(b => new BookingResponseDto
{
    BookingId = b.BookingId,
    CustomerId = b.CustomerId,
    PhotographerId = b.PhotographerId,
    SessionTypeId = b.SessionTypeId,
    StartTime = b.StartTime,
    EndTime = b.EndTime,
    Status = b.Status.ToString(),
    Notes = b.Notes
})
```

Projection allows EF Core to select only the fields required by the API response instead of loading complete related entities.

### Include vs Projection

| Approach   | Queries | Related JOINs          | Data Retrieved       |
| ---------- | ------: | ---------------------- | -------------------- |
| Include    |       2 | Customer + SessionType | More data            |
| Projection |       2 | None                   | Required fields only |

The number of queries remained the same, but projection reduced unnecessary data retrieval and JOINs.

## AsSplitQuery

An additional test was performed using a `Photographer` with two collection navigation properties:

* `Bookings`
* `ExternalSchedules`

The query was:

```csharp
var photographer = await _context.Photographers
    .Include(p => p.Bookings)
    .Include(p => p.ExternalSchedules)
    .AsSplitQuery()
    .FirstOrDefaultAsync(
        p => p.PhotographerId == photographerId);
```

`AsSplitQuery()` caused EF Core to split the operation into separate SQL queries:

```text
Photographer
    ↓
Bookings
    ↓
ExternalSchedules
```

This helps avoid excessive row duplication and potential **Cartesian Explosion** when multiple collection navigation properties are loaded together.

The experiment generated three database queries:

1. Photographer
2. Bookings
3. ExternalSchedules

## Result

Day 2 demonstrated and compared:

* Eager Loading with `Include()`
* LINQ Projection with `Select()`
* Split Queries with `AsSplitQuery()`

The main optimization focused on retrieving only the data actually required by the API.

# Day 3 — Redis Caching

## Goal

Reduce unnecessary database access for frequently requested and relatively stable data by introducing Redis caching using the **Cache-Aside Pattern**.

## Selecting a Cache Candidate

`SessionTypes` was selected as the caching candidate because it is:

* Frequently read
* Relatively stable
* Suitable for temporary caching

The endpoint was:

```text
GET /api/v1/SessionTypes
```

Highly dynamic data, such as booking status, was not selected for this simple caching strategy.

## Redis Setup with Docker

Redis was run locally using Docker:

```powershell
docker run -d --name lensbook-redis -p 6379:6379 redis:latest
```

The container was verified using:

```powershell
docker ps
```

Redis was available at:

```text
localhost:6379
```

## Redis Integration

The following package was installed:

```text
Microsoft.Extensions.Caching.StackExchangeRedis
```

`IDistributedCache` was registered in `Program.cs`:

```csharp
builder.Services.AddStackExchangeRedisCache(options =>
{
    options.Configuration =
        builder.Configuration
            .GetConnectionString("Redis");
});
```

The Redis connection string was configured as:

```json
"ConnectionStrings": {
    "DefaultConnection": "Server=(localdb)\\MSSQLLocalDB;Database=LensBookDb;Trusted_Connection=True;TrustServerCertificate=True;",
    "Redis": "localhost:6379"
}
```

The application uses the `IDistributedCache` abstraction rather than directly coupling the application logic to Redis.

## Cache-Aside Pattern

The caching flow was:

```text
Check Redis
    ↓
Cache Hit → Return cached data
    ↓
Cache Miss
    ↓
Query SQL Server
    ↓
Store result in Redis
    ↓
Return response
```

## Cache Hit / Miss Testing

The endpoint was tested twice:

| Request        | Cache State | Response Time | SQL Query |
| -------------- | ----------- | ------------: | --------- |
| First request  | Cache Miss  |       8732 ms | Yes       |
| Second request | Cache Hit   |        288 ms | No        |

The observed difference was:

**8444 ms**

The cache-hit request produced no `Executed DbCommand` log, confirming that the response was served from Redis without querying SQL Server.

These timings are treated as observed development measurements rather than a general Redis benchmark because full request timing can be affected by the development environment and other application overhead.

## Cache Invalidation

The cache key used was:

```text
sessiontypes:all
```

When a SessionType was added, the relevant cache entry was removed.

The following request then:

1. Missed the cache.
2. Retrieved the updated data from SQL Server.
3. Stored the new result in Redis.
4. Returned the updated SessionTypes.

This was tested by adding a new SessionType after the cache had already been populated.

## Result

Redis successfully reduced repeated database access for the selected read-heavy endpoint, and cache invalidation was tested to prevent stale SessionType data.

# Day 4 — Database Indexing & Performance Profiling

## Goal

Improve database query performance by identifying frequently filtered and sorted columns, adding appropriate indexes, and measuring query behavior before and after the changes.

## Identifying Index Candidates

### Bookings

The `Bookings` query frequently:

* Filters by `PhotographerId`
* Sorts by `StartTime`

Therefore, a composite index was selected:

```text
(PhotographerId, StartTime)
```

### Notifications

The `Notifications` query frequently:

* Filters by `UserId`
* Sorts by `CreatedAt`

Therefore, a composite index was selected:

```text
(UserId, CreatedAt)
```

### Photographers.UserId

`Photographers.UserId` was also reviewed as an index candidate.

However, the existing database migration already contained a unique index:

```csharp
migrationBuilder.CreateIndex(
    name: "IX_Photographers_UserId",
    table: "Photographers",
    column: "UserId",
    unique: true);
```

Therefore, no duplicate index was added.

## Composite Indexes

The indexes were configured using EF Core Fluent API:

```csharp
modelBuilder.Entity<Booking>()
    .HasIndex(b => new
    {
        b.PhotographerId,
        b.StartTime
    });
```

```csharp
modelBuilder.Entity<Notification>()
    .HasIndex(n => new
    {
        n.UserId,
        n.CreatedAt
    });
```

The column order was selected according to the actual filtering and sorting patterns of the queries.

## Migration

A new EF Core migration was created:

```text
AddPerformanceIndexes
```

The migration added:

* `IX_Bookings_PhotographerId_StartTime`
* `IX_Notifications_UserId_CreatedAt`

The existing single-column `Bookings.PhotographerId` index was removed because the new composite index better matched the query pattern.

## Performance Profiling

Performance was measured using EF Core logging and:

```text
Executed DbCommand (Xms)
```

The database command execution time was used as the main comparison metric instead of the full HTTP request duration.

### Before and After Measurements

| Query         | Before | After Run 1 | After Run 2 |
| ------------- | -----: | ----------: | ----------: |
| Bookings      |  58 ms |       66 ms |       12 ms |
| Notifications |  18 ms |       38 ms |       12 ms |

The measurements varied between executions, so they were documented as **observed results rather than guaranteed performance improvements**.

## Result

Indexes were selected based on actual query patterns, applied through EF Core migrations, and evaluated using real database execution measurements.
